The 200ms Transaction Lifecycle

An exhaustive, step-by-step breakdown of the Auth Engine's business logic, fraud gauntlet, and human operational resolution flows.

Phase 1: The Fraud Gauntlet & Compliance Alerting

Before any money is touched, the transaction must pass strict Anti-Money Laundering (AML) checks. This happens in memory within microseconds.

Step 1-2: The Webhook & Initial Routing

The sequence begins when an employee swipes a physical or virtual card. The terminal transmits the 16-digit PAN to the acquiring bank, which bounces to Visa. Because we own the BIN (Bank Identification Number), Visa forwards a strict HTTP POST /api/network/swipe webhook to our Auth Engine.

Step 3-6: The MCC Compliance Alert

The Auth Engine inspects the Merchant Category Code (MCC). If the employee is trying to buy chips at a Casino, the Auth Engine instantly rejects the transaction with an HTTP 403. Simultaneously, it fires an internal-alert-topic payload to Kafka.

Step 7-8: Human Ops Resolution (The Kill Switch)

The Notification Service consumes the Kafka event and sends an urgent email to the Risk Officer. The Human Officer logs into the internal dashboard and hits the POST /freeze endpoint. The Identity Service reaches into Redis and executes a DEL command on the card, permanently destroying its routing data so it can never be swiped again.

Phase 2: Liquidity Check & Double-Spend Prevention

If the merchant is legitimate, the system must ensure the employee has enough allocated budget, guaranteeing we do not create negative balances or double-spend scenarios.

Step 11-13: Atomic Balance Deduction

The Auth Engine hits Redis with a DECRBYFLOAT command. This is critical. Because Redis operates on a single-threaded event loop, this command subtracts the swipe amount from the wallet balance atomically, preventing two simultaneous swipes from stealing money.

Step 14-19: Insufficient Funds & Rollback

If the result of DECRBYFLOAT is negative (e.g., -15.00), the employee does not have enough budget. The Auth Engine executes an immediate INCRBYFLOAT to restore the original balance (a manual rollback). It then rejects the transaction via HTTP 400.

Step 20: The Frictionless Support Loop

Rather than waiting for the employee to call and yell at Support, the system drops a Kafka alert to the Support Desk. The Human Ops team proactively emails the employee, advising them to ask their founder for a budget increase.

Phase 3: Final Execution & Eventual Consistency

Step 22-25: Asynchronous Settlement

If the balance check succeeded (e.g., leaving a positive balance of $355.00), the Auth Engine has done its job. It drops an auth-approved-topic event onto the Kafka Bus and replies HTTP 200 OK to Visa.

Because it used a "Fire and Forget" event, it achieved its 200ms SLA constraint. The heavy database operations (saving to Postgres) are entirely offloaded to the Ledger Service, which consumes the event asynchronously whenever it is ready.
