Core Platform Features & Capabilities

Boundless FinTech isn't just a payment gateway; it is a comprehensive corporate spend management platform. The underlying Java architecture natively powers the following product features:

1. Instant Virtual Card Issuance

Company Administrators can instantly provision virtual PANs for their employees. This includes standard multi-use cards and Single-Use Burner Cards that automatically self-destruct and lock themselves in the database after their first successful transaction, completely eliminating the risk of hidden recurring subscription traps.

2. The 200ms Fraud Gauntlet

Every card swipe is intercepted in real-time. Before deducting a single cent, the Auth Engine checks the Merchant Category Code (instantly blocking casinos or crypto exchanges), enforces daily swipe velocity limits, and freezes the card if someone attempts to brute-force the CVV code.

3. Automated Receipt Chasing

Employees hate doing expenses, so Boundless automates compliance. If an employee swipes a card, a 24-hour SLA timer begins. If they fail to upload a photo of the physical receipt to our AWS S3 Bucket within 24 hours, the Ledger Service automatically triggers a freeze event, locking their card until they upload the receipt.

4. Multi-Tenant Strict Isolation

The entire architecture is designed for B2B SaaS. Using Cryptographic JWT Claims and Row-Level Security, the system guarantees mathematical isolation. A manager at Acme Corp can only view Acme Corp wallets, ensuring zero cross-contamination of financial data between clients.

5. Intelligent Alert Routing & Frictionless Support

When a transaction fails, it doesn't fail silently. If a card bounces due to Insufficient Funds, the system proactively routes an alert to the Support Desk, triggering an automated email to the employee advising them to request a budget increase. If a card fails due to restricted merchants, it routes the alert directly to the Compliance Team for human review.

CHAPTER 1: The Business Model & Domain Entities

Boundless is not a consumer bank. It is a Business-to-Business (B2B) Spend Management Platform. Our clients are startup founders and corporate treasurers (e.g., Acme Corp) who need to issue corporate credit cards to their employees for software subscriptions, travel, and expenses.

To support this, the database is strictly modeled around corporate hierarchies:

1.1 The Company Entity

Before anyone can use the platform, the legal entity must be verified via KYB (Know Your Business).

  • Attributes: companyName, einNumber (Employer Identification Number), and kybStatus (PENDING, APPROVED, FROZEN).
  • The Freeze Mechanism: If the Risk & Compliance team detects money laundering, they flip the company's kybStatus to FROZEN. This instantly cascades, freezing every Master Wallet, every Employee Wallet, and every Virtual Card associated with that Tenant.

1.2 The Master Wallet

This is the lifeblood of the tenant. Boundless does not extend credit. We are a pre-paid platform.

  • The Flow: Acme Corp wires $100,000 of real USD from their Chase Bank account to Boundless's master treasury account.
  • The Minting: The Boundless ROLE_PLATFORM_TREASURY officer intercepts that wire, logs into the Internal Ops portal, and mints $100,000 of digital liquidity into Acme Corp's MasterWallet.
  • Constraint: The MasterWallet is a singular pool. Employees cannot swipe directly against it.

1.3 The Employee Wallet

To allow an employee to spend money, the Company Admin must carve out a specific budget.

  • The Allocation: If a founder wants to give an employee a $500 travel budget, the system atomically deducts $500 from the MasterWallet and moves it into the Employee's Wallet.
  • Isolation: An employee can have multiple wallets (e.g., "Software Subscriptions", "Travel", "Per Diems"), each with its own isolated balance.

1.4 The Virtual Card (The PAN)

The virtual card is the 16-digit Primary Account Number (PAN) that the employee actually types into Amazon or hands to a barista.

  • The Binding: Every card is strictly bound to exactly one Wallet (Foreign Key: wallet_id).
  • Card Types: Cards can be STANDARD (multi-use, recurring) or BURNER (single-use, auto-destructing).

CHAPTER 2: Multi-Tenancy & Row-Level Security

Because Boundless hosts multiple competitor companies (Acme Corp and Globex) in the exact same PostgreSQL database, data leakage is catastrophic. We prevent this using strict Row-Level Security (RLS) enforced at the application layer.

2.1 The Identity Binding

Every User in the database has a companyName column. This is the tenant identifier. When a user logs in, the JwtService embeds their companyName inside the cryptographically signed JWT payload.

2.2 Endpoint Isolation

When the Acme Corp Admin hits the GET /api/company-admin/employees endpoint, the CompanyAdminController extracts the companyName directly from the JWT Context. It executes: SELECT * FROM users WHERE companyName = 'Acme Corp'. It is mathematically impossible for the Acme Admin to query or view employees belonging to Globex, because the WHERE clause is hardcoded to their authenticated JWT identity.

2.3 Financial Isolation

When the Acme Corp Admin tries to issue a card to an employee UUID:

  1. The controller looks up the target Employee.
  2. It compares Employee.companyName against Admin.companyName.
  3. If they do not match exactly, the system throws a SecurityException: Cannot fund an employee outside your company! and drops a proactive alert to the internal security team.

The Difference Between Budget Allocation & External Spending

There is a strict architectural difference between Internal Allocation and External Spending:

  • Internal Allocation (Day 0): When a Company Admin creates an Employee Wallet for $1,000, no real money leaves the platform. The system simply deducts $1,000 from their Master Wallet and assigns it to the Employee Wallet in Postgres. The money is still safely in our partner bank.
  • External Spending: When an employee actually swipes their card, no physical money moves at that exact second. It happens in two distinct phases:

    Phase 1: The Digital Hold (Day 1 - What our code does)

    When Bob buys a $5 coffee at Starbucks, Starbucks' card reader asks Visa, "Is Bob good for this?" Visa asks our Auth Engine. Our Auth Engine checks Redis, subtracts $5 from Bob's digital balance, and tells Visa, "Yes, approved!"

    At this exact moment, no real money has moved. Our system just put a digital "hold" on the $5 so Bob can't spend it again. Starbucks gives Bob the coffee based on our digital promise to pay them later.

    Phase 2: The Real Money Move (Day 3 - Clearing & Settlement)

    At the end of the day, Starbucks tells Visa, "Okay, it's time to pay up for all the coffees sold today."

    • The Settlement File: A few days later, Visa generates a massive spreadsheet (a "Settlement File") listing all the approved transactions and sends it to our real-world partner bank (e.g., Sutton Bank, where we hold the physical corporate cash).
    • The Bank Wire: Our partner bank looks at the spreadsheet, takes $5 of real physical USD out of our vault, and wires it to Visa's bank. Visa then wires it to Starbucks' bank.
    • The Reconciliation: Our Boundless Ledger Service downloads a digital copy of that spreadsheet, matches it against our PostgreSQL database, and changes the transaction status from PENDING to SETTLED.

    In short: our Java code manages the digital rules and balances to prevent overspending in milliseconds, but the real physical money is moved asynchronously by the banks reading massive spreadsheets days later.

CHAPTER 4: The Fast Path (The 200ms Auth Engine)

Virtual Card Issuance & Expiry

When a Company Admin creates a wallet, a 16-digit Virtual Card is instantly generated. To comply with standard card network rules, every card is automatically assigned an Expiry Date exactly 3 years from the date of issuance alongside a 3-digit CVV.

The auth-engine-service is the crown jewel of the platform. When a card is swiped at a terminal, Visa fires a webhook to POST /api/network/swipe. Visa requires a response in under 200 milliseconds. If the system takes 201ms, Visa drops the connection and declines the card.

To achieve this, the Auth Engine completely ignores PostgreSQL. Disk I/O is too slow. It relies entirely on a pre-warmed Redis In-Memory Data Grid.

4.1 The Redis Synchronization

When the Identity Service issues a card, it doesn't just save it to Postgres. It pushes critical O(1) routing data to Redis:

  • SET card:{pan}:wallet {wallet_id}
  • SET wallet:{wallet_id}:balance 500.00
  • SET card:{pan}:type STANDARD

4.2 The Chain of Responsibility Gauntlet

When the Visa webhook arrives, the FraudEngine class runs it through a gauntlet of Java rules. If any rule fails, the chain breaks and a 400 Bad Request is returned.

  1. Velocity Rule: The system calls INCR velocity:{pan}:{YYYY-MM-DD} in Redis. If the returned integer is > 10, the card has been swiped too many times today. Decline.
  2. Merchant Category Code (MCC) Rule: The system checks the merchantName string against a highly restricted regex blacklist. "Las Vegas Casino", "Local Dive Bar", and "Binance Crypto" trigger an instant decline and a Kafka alert to Compliance.
  3. Brute Force Rule: If the CVV provided by Visa doesn't match, INCR cvv_failures:{pan} is called. If the hacker hits 3 failures, the card is locked for 24 hours. Decline.
  4. The Balance Rule (The Core Logic):
    • The system looks up the wallet: GET card:{pan}:wallet.
    • It executes an atomic DECRBYFLOAT wallet:{wallet_id}:balance {amount}.
    • If the resulting balance is negative (e.g., -5.00), it immediately reverses it (INCRBYFLOAT) and throws an Insufficient Funds exception.
    • If positive, the transaction is approved!

4.3 The Single-Use Burner Sequence

If the card passes the gauntlet, the Auth Engine checks GET card:{pan}:type. If the string equals BURNER, the Auth Engine executes a self-destruct. It calls DEL card:{pan}:wallet and DEL card:{pan}:status. The card ceases to exist in the Fast Path memory. If a hacker steals the number and tries to use it 5 seconds later, the Auth Engine will return "Card Not Found".

CHAPTER 5: The Slow Path (Ledger & SLA Compliance)

Because the Auth Engine has no time to write to PostgreSQL or enforce corporate receipt policies, it relies on Event-Driven Architecture. When the Auth Engine approves a swipe, it publishes an auth-approved-topic string to Apache Kafka and returns 200 OK to Visa. Its job is done.

5.1 Asynchronous Settlement

The ledger-service listens to auth-approved-topic. When it consumes the event, it parses the JSON and executes a heavy INSERT INTO transaction_ledger SQL statement. This permanently records the financial history for tax auditors.

5.2 The RBI OTP Mandate

If the swipe amount is massive (e.g., > ₹5,000), the Reserve Bank of India (RBI) requires 2-Factor Authentication.

  • The Auth Engine halts the transaction, returning 202 PENDING_OTP to Visa.
  • It generates a 6-digit code, saves SET otp:{pan} 123456 EX 300 in Redis.
  • It drops an otp-email-topic Kafka event.
  • The Notification service emails the code to the employee's phone.
  • The transaction is frozen in mid-air until the employee proves their identity.

5.3 The 24-Hour Receipt SLA (The Enforcer)

Corporate tax law requires physical receipts for large purchases. Boundless automates this entirely.

  1. The Warning: The moment a $50+ transaction settles, the Ledger Service drops a receipt-reminder-topic event. The employee immediately gets an email: "Please upload your receipt within 24 hours."
  2. The Cron Job: Inside the Ledger Service is a Spring @Scheduled method running every 5 minutes.
    • It queries: SELECT * FROM transaction_ledger WHERE amount > 50 AND receiptUploaded = false AND created_at < (NOW - 24 HOURS).
    • If it finds a guilty transaction, it drops a card-freeze-topic event to Kafka.
  3. The Freeze: The Identity Service consumes the freeze event. It executes SET card:{pan}:status FROZEN in Redis.
    • Result: The employee is stranded at a restaurant and their card is declined until they do their expense reports!

5.4 S3 Object Storage Unfreezing

To unlock their card, the employee must upload an image.

  1. They hit POST /api/transactions/{id}/receipt with a Multipart File.
  2. The Ledger Service connects to MinIO (AWS S3 Compatible Storage) and streams the image bytes into the boundless-receipts bucket.
  3. It saves the public s3Url in Postgres and sets receiptUploaded = true.
  4. It fires a card-unfreeze-topic Kafka event.
  5. The Identity Service hears it and calls DEL card:{pan}:status in Redis. The card is instantly active again!

7.2 The 200ms Transaction Sequence (Data Flow)

When an employee swipes their card, the data flow is strictly controlled to ensure atomic deductions and absolute speed.

Exhaustive Step-by-Step Execution Breakdown

Initial Webhook Injection

  • Step 1: The Employee physically swipes their virtual card at a terminal.
  • Step 2: Because we own the Visa BIN routing, the terminal bounces the request to Visa, which fires an HTTP POST payload containing the JSON transaction data into our Auth Engine.
  • Step 3: The Auth Engine immediately executes a self-check on the Merchant Category Code (MCC) to ensure the terminal isn't a prohibited merchant.

Branch A: The Compliance Failure Flow (e.g., Casino Swipe)

  • Step 4: The Auth Engine detects the restricted MCC and instantly publishes an event to the internal-alert-topic in Kafka.
  • Step 5: The Notification Service asynchronously consumes that Kafka event.
  • Step 6: The Notification Service dispatches an urgent SMTP email to the Human Ops (Compliance) team.
  • Step 7: Simultaneously, the Auth Engine replies to Visa with an HTTP 403 Forbidden, declining the card at the terminal.
  • Step 8: The Human Ops Analyst reads the email and hits the POST /api/internal-ops/companies/freeze endpoint.
  • Step 9: The Identity Service connects to the Redis Grid and fires a DEL card command, permanently deploying the kill switch and destroying the card's routing data.

Branch B: The Legitimate Merchant Flow & Liquidity Check

  • Step 10: If the MCC was valid, the Auth Engine hits Redis with an INCR velocity command to ensure the card hasn't hit its daily swipe limit.
  • Step 11: The Auth Engine then executes a DECRBYFLOAT command against the Redis Grid to atomically subtract the swipe amount from the employee's wallet.

Branch C: The Liquidity Failure Flow (Insufficient Funds)

  • Step 12: Redis returns a negative float (e.g., -15.00), proving the employee does not have enough budget.
  • Step 13: The Auth Engine executes a manual rollback using an INCRBYFLOAT command to restore the original balance.
  • Step 14: The Auth Engine publishes an event to the internal-alert-topic targeting the Support Desk.
  • Step 15: The Notification Service consumes the Kafka event.
  • Step 16: The Notification Service sends an SMTP email to the Customer Support team.
  • Step 17: Simultaneously, the Auth Engine rejects the swipe at the terminal via HTTP 400 Bad Request.
  • Step 18: The Human Support Agent proactively emails the Employee advising them to request a budget increase from their founder.

Branch D: The Final Success Flow & Asynchronous Settlement

  • Step 19: If the employee had sufficient funds, Redis returns a positive float (e.g., 355.00).
  • Step 20: The Auth Engine drops an auth-approved-topic event onto the Apache Kafka bus (Fire and Forget).
  • Step 21: The Auth Engine replies HTTP 200 OK to Visa, approving the transaction in under 200 milliseconds. The heavy disk I/O operations are left to the Ledger Service which will asynchronously consume Step 20 later.

CHAPTER 8: Implemented Fault Tolerance & Internal Ops

Unlike theoretical architectures, the following mechanisms are strictly implemented in the underlying Java codebase and active in the docker-compose cluster.

8.1 Database Contention & Transaction Rolling (Implemented)

If the Auth Engine detects Insufficient Funds, it executes a strict rollback in Redis. Because we use DECRBYFLOAT to atomically deduct balances, if the result is negative, the Auth Engine immediately executes an INCRBYFLOAT to restore the exact amount, returning an HTTP 400 Bad Request to the terminal. This prevents the "Double Spend" problem natively in the code.

8.2 S3 Blob Storage Offloading (Implemented)

To prevent PostgreSQL from crashing under the weight of thousands of JPEG receipt uploads, we integrated MinIO (Local AWS S3) in our docker-compose.yml. When a user hits the Ledger Service to upload a receipt, the Java code uses the aws-java-sdk-s3 to stream the bytes directly to the boundless-receipts bucket on Port 9000, and only saves the lightweight s3Url string in Postgres.

CHAPTER 9: Implemented Alert Resolution (Notification Service)

When the Auth Engine publishes to the internal-alert-topic, we implemented a Universal Routing Engine that categorizes the failure and routes it to specific internal teams via the Notification Service (which consumes the topic and fires JavaMailSender SMTP emails).

9.1 Compliance Routing (e.g., Casino Swipe / Brute Force)

  • The Code: If the MCC is restricted, the Auth Engine builds a payload targeting ROLE_PLATFORM_COMPLIANCE.
  • The Resolution: The Notification Service receives the Kafka event and emails the internal Compliance Team. The analyst logs in and hits our implemented /api/internal-ops/companies/{name}/freeze endpoint in the Identity Service, which flips the Postgres status to FROZEN.

9.2 Customer Support Routing (e.g., Insufficient Funds)

  • The Code: If the Redis balance check drops below zero, the Auth Engine routes the failure to ROLE_PLATFORM_SUPPORT.
  • The Resolution: The Notification Service emails the Customer Support desk with the exact reason for the decline, allowing them to proactively email the employee explaining why their card bounced.

9.3 Treasury Routing (e.g., Master Wallet Depleted)

  • The Code: If a Company Admin tries to fund an employee wallet but their Master Wallet is empty, the Identity Service drops an alert targeting ROLE_PLATFORM_TREASURY.
  • The Resolution: The Notification Service emails the Treasury Team, who can then manually contact the client for a bank wire, and then use our implemented POST /api/internal-ops/master-wallet/fund endpoint to restore liquidity.

9.4 Asynchronous KYB Onboarding (Human-in-the-Loop)

To prevent malicious actors from gaining access to the platform, Boundless does not auto-approve new corporate registrations. We implemented a strict asynchronous, human-in-the-loop KYB (Know Your Business) workflow.

  • The Registration: When a founder hits POST /api/public/register-company, the system saves the company to PostgreSQL but hardcodes their kybStatus to PENDING_MANUAL_REVIEW. No Master Wallet is created, meaning no money can be moved.
  • The Alert: The API drops an event onto the Kafka internal-alert-topic. The Notification Service consumes this and fires an urgent email to the internal Compliance Team containing the company's EIN (Tax ID).
  • The Security Boundary: Once the human officer verifies the EIN externally, they log into the Boundless Admin Dashboard. They must possess a JWT containing the ROLE_PLATFORM_COMPLIANCE authority.
  • The Execution: The officer hits POST /api/internal-ops/companies/{name}/approve. Because they have the correct cryptographic role, the Spring Security @PreAuthorize check passes. The system flips the status to APPROVED and dynamically generates the company's Master Wallet, officially unlocking their ability to issue cards.

CHAPTER 11: Observability & Distributed Tracing

Because Boundless is a highly decoupled, asynchronous microservices architecture, tracking a single transaction as it jumps from the API Gateway, to the Auth Engine, into Kafka, and finally to the Ledger is impossible using standard log files. To solve this, the platform utilizes OpenTelemetry and Zipkin.

The Trace Lifecycle

  1. Generation: When a request hits the API Gateway, Spring Cloud Sleuth/Micrometer automatically generates a unique 64-bit traceId (e.g., a3c5f9b42e...).
  2. HTTP Propagation: The API Gateway forwards the request to the Auth Engine, injecting the traceId into the traceparent HTTP header.
  3. Kafka Propagation: When the Auth Engine publishes an event to Kafka, the traceId is automatically injected into the Kafka Message Headers.
  4. Visualization: Every microservice asynchronously fires spans to the Zipkin Server (Port 9411) via OpenTelemetry. Engineers can open the Zipkin Web UI, paste the traceId, and view a visual waterfall chart of the entire lifecycle, instantly identifying bottlenecks (e.g., "The Ledger took 40ms to write to Postgres").

CHAPTER 12: The Saga Pattern (Distributed Transactions)

Because microservices utilize separate databases (Redis vs PostgreSQL), a standard SQL ROLLBACK cannot save the system if a multi-step transaction fails. Boundless utilizes a Choreographed Saga Pattern to ensure zero data loss.

The Compensating Rollback Flow

  1. The Hold: The Auth Engine deducts the balance in Redis and fires an event to Kafka.
  2. The Failure: The Ledger Service attempts to save the transaction to PostgreSQL. If the database crashes, the Ledger catches the exception.
  3. The Compensation Event: The Ledger Service publishes the exact transaction payload to the transaction-failed-compensation-topic in Kafka.
  4. The Refund: The Auth Engine consumes the compensation event, looks up the wallet routing, and executes a Redis INCRBYFLOAT to perfectly refund the employee's wallet, reversing the original DECRBYFLOAT.
🧪 Sandbox Testing (The Magic Amount): To test this Saga rollback safely on your local machine, simulate a swipe for exactly $13.37. The Ledger Service contains a hardcoded trigger that will artificially throw a PostgreSQL Connection Timeout for this exact amount, instantly initiating the full Kafka compensation rollback!

CHAPTER 13: Enterprise Features (V2 Expansion)

In the V2 update, Boundless evolved from a simple ledger into a highly intelligent, real-time financial platform. Here is a simple, easy-to-understand breakdown of how each new feature flows under the hood.

1. The Live Dashboard (WebSockets) 📡

The Goal: When someone swipes their card at Starbucks, the company manager should see it pop up on their screen instantly, without ever refreshing the page.

The Flow:

  • Step 1 (Connection): You open the browser. Your browser connects to the Ledger Service and keeps a permanent "tunnel" open (a WebSocket).
  • Step 2 (Trigger): An employee swipes their card. The transaction successfully settles in the database.
  • Step 3 (Push): The moment it saves to the database, Java packages the transaction data into a JSON message and fires it down the open tunnel (the /topic/transactions channel).
  • Step 4 (Display): Your browser catches the message and instantly paints a new card on the screen.

2. Multi-Currency Wallets 🌍

The Goal: Allow an employee to buy a train ticket in London (GBP) using a US company card (USD), while charging the exact correct amount based on today's exchange rate.

The Flow:

  • Step 1 (Swipe): The card is swiped for £100 GBP.
  • Step 2 (Fetch Rate): The CurrencyService instantly reaches out to an external Foreign Exchange API to ask: "What is the live exchange rate for GBP to USD?"
  • Step 3 (Fallback): If the FX API is down, the system is smart enough to use a hardcoded "safety fallback" rate so the employee isn't stranded at the train station.
  • Step 4 (Record): The Ledger saves both numbers: the original £100 GBP (so the employee recognizes the charge on their app) and the converted $125 USD (so the company's accounting adds up).

3. Smart Receipt OCR (Gemini AI) 📸

The Goal: Stop forcing accountants to manually read coffee receipts. Let an AI do it automatically.

The Flow:

  • Step 1 (Upload): An employee takes a photo of a receipt and uploads it via the API.
  • Step 2 (Storage): The image is securely uploaded to a Cloudinary bucket for permanent storage, and the URL is saved.
  • Step 3 (AI Vision): The actual image bytes are piped to Google's Gemini 2.0 Flash Vision AI. We prompt Gemini: "Read this receipt and tell me the total amount and the merchant name."
  • Step 4 (Auto-Match): The system takes Gemini's extracted text and mathematically compares it against the database. If Gemini saw "$5.00 Starbucks" and the database says "$5.00 Starbucks", the system marks the transaction's audit status as MATCHED.

4. The Immutable Audit Trail 📜

The Goal: Make sure no one (not even a hacker or rogue employee) can silently alter financial history without leaving a permanent footprint.

The Flow: Every time something important happens (a card is frozen, a receipt is uploaded, currency is converted), the system writes a permanent log into an AuditLog table. This table is "append-only", meaning accountants can always look back to see exactly who did what and when. It is the ultimate financial security camera.

5. B2B Webhook Engine 🔔

The Goal: Let large corporate clients connect their own custom software to our platform, so they get instant programmatic alerts when their employees spend money.

The Flow:

  • Step 1 (Register): A client registers their company's server URL (e.g., https://api.mycompany.com/webhook) with us.
  • Step 2 (Event): An employee spends money.
  • Step 3 (Package): In the background, our Ledger Service wraps the transaction data into a JSON package.
  • Step 4 (Security): To prove the message came from us (and not an imposter), we mathematically "sign" the message using a shared secret password (an HMAC-SHA256 hash).
  • Step 5 (Fire): We shoot the JSON package over to the client's URL asynchronously.

6. AI Financial Storytelling 🧠

The Goal: Instead of making the CEO stare at an Excel spreadsheet with 10,000 rows, let an AI summarize the company's financial health as a story.

The Flow:

  • Step 1 (Query): You hit the /story endpoint.
  • Step 2 (Data Scoop): Java scoops up all the raw transaction data from PostgreSQL (amounts, merchants, dates, receipt status).
  • Step 3 (Prompt Injection): Java dynamically builds a giant text prompt: "You are a CFO. Read this data and write a report called 'Where Did The Money Go?'. Tell me the red flags."
  • Step 4 (Generate): Gemini analyzes the data and replies with a beautifully formatted, plain-English executive summary highlighting exactly who spent the most and where the company can save money!

CHAPTER 14: API Gateway Security (Authentication & Authorization)

In a microservices architecture, each service is a completely independent application. Rather than duplicating security logic across every service, Boundless uses a centralized API Gateway on port 8080 as the single security checkpoint for the entire platform.

How The Security Flow Works 🔐

The Goal: No unauthenticated user should ever be able to access any business API (transactions, insights, webhooks, audit logs). Only the login and public registration endpoints are open.

The Flow:

  • Step 1 (Login): The user hits POST /api/auth/login with their email and password. The Identity Service validates the credentials and returns a signed JWT token containing the user's email, userId, and role.
  • Step 2 (Request): For every subsequent API call, the user includes the token in the Authorization: Bearer <token> header.
  • Step 3 (Gateway Intercept): The API Gateway (GatewayAuthFilter) intercepts the request before it reaches any downstream service. It checks: is the endpoint public? If not, is there a valid JWT token?
  • Step 4 (JWT Validation): The Gateway decodes the JWT using the same shared secret key that the Identity Service used to sign it. If the token is expired, tampered with, or missing, the Gateway immediately returns 401 UNAUTHORIZED and the request never reaches the downstream service.
  • Step 5 (Header Injection): If the token is valid, the Gateway extracts the user's identity (email, role, userId) and injects them as trusted internal headers (X-Trusted-User-Email, X-Trusted-User-Role, X-Trusted-User-Id) before forwarding the request downstream.
  • Step 6 (Downstream Trust): The downstream service (e.g., Ledger Service) simply reads these trusted headers to know WHO is making the request. It never needs to decode JWT itself — the Gateway already did the hard work.

The Shared JWT Secret Key 🔑

Both the card-identity-service (which generates tokens) and the api-gateway-service (which validates tokens) share the exact same secret key configured in their application.yml files:

jwt.secret: YOUR_JWT_SECRET_KEY_MUST_BE_AT_LEAST_256_BITS_LONG_CHANGE_ME!

This key is used with HMAC-SHA256 to sign and verify tokens. If anyone tampers with even a single character in the JWT payload, the signature verification will fail and the Gateway will reject the request instantly.

CHAPTER 15: Cross-Microservice Security & Internal APIs

In a distributed system, backend services often need to fetch data from one another without exposing those capabilities to the public internet. Boundless FinTech secures internal service-to-service communication using strict API Gateway Isolation and Cross-Microservice Authorization.

1. Gateway Blocking & Isolation

The api-gateway-service (Port 8080) acts as the impenetrable front door to the platform. If you inspect the routing rules in the Gateway's configuration, the /api/internal/** path is deliberately omitted from the routing predicates.

# API Gateway Configuration
routes:
  - id: card-identity-service
    uri: http://localhost:8081
    predicates:
      # /api/internal/** is MISSING intentionally!
      - Path=/api/auth/**, /api/public/**, /api/admin/**, /api/employees/**

If a hacker attempts to execute a direct attack on http://localhost:8080/api/internal/verify-card-ownership, the Gateway immediately drops the traffic and returns a 404 Not Found. Internal endpoints can only be accessed directly over the private backend network (e.g., localhost:8081).

2. The "verify-card-ownership" API (Preventing IDOR Attacks)

When an employee uploads a receipt to the Ledger Service, the Ledger Service is functionally "blind" to identity—it only records transaction math. If left unchecked, a malicious employee could guess someone else's transactionId and upload fake receipts to their account (an Insecure Direct Object Reference / IDOR vulnerability).

To prevent this, the Ledger Service executes a real-time HTTP handshake with the Identity Service:

  • Step 1: The Ledger Service intercepts the user's JWT token and fires a background HTTP GET request to the Identity Service: /api/internal/verify-card-ownership?cardNumber=XYZ
  • Step 2: The Identity Service decodes the forwarded JWT, extracts the Employee's email, and queries the database to see if that email legally owns the credit card.
  • Step 3: The Identity Service returns a boolean true or false.
  • Step 4: If false, the Ledger Service immediately blocks the file upload and returns a 403 Forbidden.

3. Data Enrichment (Notification Service)

Kafka events (like "Card 1234 Requires an OTP") intentionally do not contain PII like email addresses. When the Notification Service consumes an event from Kafka, it executes a silent HTTP lookup against the Identity Service (/api/internal/cards/{cardNumber}/email) to retrieve the target's email address right before dispatching the SMTP payload. This keeps the Kafka event stream completely sanitized of PII.

⚠️ SECURITY LESSON: The @EnableMethodSecurity Bug

During early development, the InternalOpsController was protected by @PreAuthorize("hasRole('PLATFORM_TREASURY')"), but the Identity Service's SecurityConfig.java lacked the @EnableMethodSecurity toggle. Because this annotation was missing, Spring Boot silently bypassed every method-level security check in the entire service. This allowed a Company Admin to successfully hit the /master-wallet/fund endpoint. The toggle has since been activated, sealing the privilege escalation vulnerability.

CHAPTER 16: Observability & Distributed Tracing

Because Boundless is a highly decoupled, asynchronous architecture, tracking a single transaction as it jumps from the API Gateway, to the Auth Engine, into Kafka, and finally to the Ledger is impossible using standard log files. To solve this, the platform utilizes Micrometer Tracing, Brave, and Zipkin via micrometer-tracing-bridge-brave.

1. The Trace Lifecycle

  • Generation: When a request hits the API Gateway (Port 8080), Micrometer automatically generates a unique 64-bit traceId (e.g., a3c5f9b42e...).
  • HTTP Propagation: The API Gateway forwards the request to the Auth Engine, injecting the traceId into the b3 HTTP headers.
  • Kafka Propagation: When the Auth Engine publishes an event to Kafka, the traceId is automatically injected into the Kafka Message Headers.
  • Visualization: Every microservice asynchronously fires spans to the Zipkin Server (Port 9411) over HTTP via a custom TracingConfig BytesMessageSender.

2. Interpreting the Zipkin UI

When you open Zipkin and query for recent traces, you will see a list of rows. Each row represents a single, distinct request or event that entered the system.

  • Spans Count: A higher number (e.g., 13 spans) indicates a distributed transaction that bounced around multiple components or services.
  • Root Trace Name: The name of the trace (e.g., auth-engine-service: http post /api/network/swipe) tells you the "Root" entry point of that request. If you hit a service directly, that service is the root. If you go through the API Gateway, the Gateway will be the root.

3. The Waterfall View (Trace Details)

Clicking SHOW on a trace opens the Waterfall view, which visually breaks down where the time went:

  • The Root Span (Top Bar): Represents the total time the request spent inside the entry service.
  • Child Spans (Cascading Bars): Every time the code makes a call to an external database, cache, or API, it is recorded as a child span. For example, you will see redis: exists, redis: get, and redis: set spans cascading below the Auth Engine root span. This proves exactly how many milliseconds the Redis O(1) Data Grid lookups took during the authorization phase.
  • Missing Downstream Services: If a trace stops at the Auth Engine and never shows Kafka spans reaching the Ledger or Notification services, it means the transaction was halted (e.g., declined for insufficient funds or flagged for a 3DS OTP step-up challenge).
💡 Pro Tip for Testing Traces:

If you test a swipe by hitting the auth-engine-service port directly (8082), the API Gateway will not appear in the trace. Always send requests through the Gateway (8080) to see the full end-to-end trace graph!
